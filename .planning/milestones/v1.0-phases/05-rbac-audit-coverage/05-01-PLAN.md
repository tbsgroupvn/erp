**Group A: @Public() at CLASS level** (infrastructure/public endpoints -- no auth required):
- `core/health/health.controller.ts` -- K8s probes, must be unauthenticated
- `modules/health/health.controller.ts` -- duplicate health check, same reason
- `core/metrics/metrics.controller.ts` -- Prometheus scraper endpoint
- `modules/public/public-cms.controller.ts` -- public website CMS content

For each: import `Public` from `@common/decorators/public.decorator` and add `@Public()` at CLASS level (before `@Controller()`). Do NOT add JwtAuthGuard or RolesGuard.

**Group B: @Roles(...ALL_ROLES) at CLASS level** (any authenticated user):
- `modules/chat/chat.controller.ts` -- workplace messaging
- `modules/calendar/calendar.controller.ts` -- workplace calendar
- `modules/drive/drive.controller.ts` -- workplace file storage
- `modules/wiki/wiki.controller.ts` -- workplace wiki
- `modules/video/video.controller.ts` -- workplace video meetings
- `modules/search/search.controller.ts` -- global search
- `modules/attendance/attendance.controller.ts` -- employee attendance
- `modules/attendance/attendance-gps.controller.ts` -- GPS check-in

**Class-level @Roles(...ALL_ROLES) is acceptable here.** RESEARCH.md warns against class-level `@Roles()` with restrictive role sets (e.g., `@Roles(CEO, COO)` at class level would silently deny other roles on all methods). However, `@Roles(...ALL_ROLES)` at class level is explicitly recommended in RESEARCH.md Example 2 and Pitfall 4 for workplace controllers where ALL authenticated users need access. This is self-documenting: it signals "any authenticated user may call any endpoint on this controller." If a future method on these controllers needs restricted access, a method-level `@Roles()` will override the class-level one via NestJS's `getAllAndOverride()` behavior.

For each: import `Roles` from `@common/decorators/roles.decorator` (or `@core/rbac/decorators/roles.decorator`), import `ALL_ROLES` from `@core/rbac/roles.enum`, import `RolesGuard` from `@common/guards/roles.guard` (or `@core/rbac/guards/roles.guard`). Add `@Roles(...ALL_ROLES)` at CLASS level. Ensure `@UseGuards(JwtAuthGuard, RolesGuard)` is present (add RolesGuard if only JwtAuthGuard exists). Match the import style already used in that file.

**Group C: Role-specific at CLASS or METHOD level** (restricted access):
- `modules/customer-portal/customer-portal.controller.ts` -- This is accessed by sales/CSKH roles for customer portal impersonation. Add `@UseGuards(JwtAuthGuard, RolesGuard)` if not present, add `@Roles(...ALL_ROLES)` at class level (customer portal is used by many roles). If specific methods clearly belong to restricted roles, use method-level @Roles. When in doubt, use ALL_ROLES at class level.
- `modules/approval/delegation/delegation.controller.ts` -- Approval delegation is for managers. Add `RolesGuard` to existing `@UseGuards(JwtAuthGuard)`, add `@Roles(...ALL_ROLES)` at class level (any authenticated user might need to delegate approvals).

**Import pattern**: Match the import path convention used in each file. If the file already imports from `@common/guards/`, use that path. If it uses `@core/rbac/`, use that. The ROLES_KEY value is identical regardless of import source.
